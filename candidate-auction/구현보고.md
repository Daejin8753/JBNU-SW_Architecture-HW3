## 5. 품질 문제 → 해결 → 남은 한계

| 문제 | 해결 | 남은 한계 |
|---|---|---|
| 같은 경매 동시 입찰 경합 | 경매별 `Lock`, now 를 잠금 뒤에 정함, 입찰+상태 변경 한 트랜잭션 | 잠금 dict 가 경매 수만큼 커진다 |
| 마감과 입찰 겹침 | 둘 다 같은 경매 잠금, `now >= ends_at` 이면 409, 마감은 `open` 아니면 무시 | Condition.wait 의 깨어남 오차(시험에서 0.5초 안) |
| 플러그인이 저장소를 직접 만짐 | import 허용 목록 정적 검사 + ctx 허용 목록(`audit.write` 만) | 샌드박스가 아님(`__builtins__` 우회 가능) |
| 플러그인 결함이 코어를 멈춤 | 예외·출력 위반 집계, 연속 3회 `disabled`, 선택 단계(알림)는 `notify_error` | inproc 무한 루프는 못 끊음 |
| 별도 프로세스가 멈춤 | 자식당 Lock, 잠금 대기·시간 제한·kill→wait(2), 다음 요청이 재기동 | 알림이 멈추면 입찰 응답이 최대 8초 늦음 |
| 진행 중 호출과 제거·재설치 섞임 | inflight 계수, 진행 중 install 409, 마지막 호출 끝에 정리, 집계는 같은 generation 만 | remove 가드(경매 사용 여부) 확인과 상태 변경 사이 짧은 경합 |
| 방식 장애 중 마감 | `settle_pending` + 사유 저장, 다시 켜면 그 방식의 정산 대기 경매 재정산 | 그 방식이 계속 고장이면 대기로 남음 |
| 비공개 방식 노출 | 마감 전 공개 정보는 `view` 결과만, view 실패 시 입찰 수만 | 알림 SSE 는 모든 구독자에게 가고 브라우저가 이름으로 거른다(인증 없음) |
| SSE 가 서버 종료를 막음 | 구독 큐에 종료 표시, daemon_threads | 큐가 차면 그 구독을 끊고 브라우저가 다시 연결 |
| 실행 데이터 유실 | sqlite WAL, plugins.json 임시 파일 + os.replace | trace 는 메모리뿐 |

## 7. 지시에 없어서 직접 정한 것

1. plugins.json 이 없는 첫 실행: MANIFEST `autoload` 가 False 가 아닌 플러그인을 모두 설치한다(broken_type 만 `autoload: False`). future_contract 는 그래서 첫 실행에 `rejected` 로 보인다.
2. `rejected` 는 plugins.json 에 남기지 않는다(값이 active·disabled 뿐이므로). 두 번째 실행부터 future_contract 는 `available` 이고 [설치]를 누르면 `rejected` 가 된다. remove 는 plugins.json 항목을 지운다.
3. 수명주기 오류 code 두 개 추가: `conflict`(409: 설치 중, 진행 중 호출, 제거 거부, 마감된 경매 입찰), `not_found`(404).
4. 입력 계약 위반은 `rejected`(400)로 돌려주고 장애로 세지 않는다(코어가 만든 입력이므로 플러그인 책임이 아님). 확장점에 없는 op 도 같다.
5. `Rejected` 는 연속 실패 수를 바꾸지 않는다(0으로 되돌리지도 않음). 장애 때 reason 에 마지막 장애 문장을 둔다.
6. generation 은 install 시도마다 +1 한다(rejected 로 끝나도).
7. inproc 호출 때 payload 를 deepcopy 해서 넘긴다. process 플러그인에는 ctx 대신 None 을 넘긴다.
8. process 자식이 `{"ok": false, "error"}` 로 답하면 장애 1회로 세지만 자식은 죽이지 않는다(프로토콜은 정상이므로).
9. 마감(`closed`) 된 경매는 목록·상세에 모든 입찰을 공개한다. `settle_pending` 은 아직 `view` 결과만 낸다. `view` 가 실패하면 `current_price: null`, `visible_bids: []`, `bid_count` 만 내고 `view_error` 를 붙인다.
10. english 의 `view.price` 는 입찰이 없으면 None(화면은 시작가를 따로 보여 준다). dutch 는 amount 가 와도 무시한다. english·sealed 에서 amount 가 없으면 Rejected.
11. 물품명 1~100자(앞뒤 공백 제거). 경매 id 는 12자 16진수, 입찰 id 는 `<경매id>_<순번 5자리>`.
12. 입찰 경로에서 응답용 `view` 는 경매 잠금 안에서 부른다.
13. 알림은 notifier 결과 중 user·message 가 문자열인 항목만 저장한다. SSE `notification` 은 모든 구독자에게 user 필드와 함께 보내고, 브라우저가 자기 이름 것만 보여 준다.
14. 경매 방식 목록 API 를 따로 두지 않았다. 화면은 `/api/plugins` 에서 `active` 인 `auction_type` 을 고른다.
15. `/api/trace*`, `/api/events` 는 trace 를 만들지 않는다. 예약 마감은 `clock close <id>` trace 를 만들고 첫 hop 은 `internal:clock → kernel` 이다. hop 이름은 `http_adapter`, `kernel`, `registry`, `plugin:<이름>`, `internal:<서버>`.
16. Host·Origin 검사는 POST 에만 한다. 경로는 맞고 메서드가 다르면 404. 응답은 HTTP/1.0(요청마다 연결 닫음).
17. SSE 큐가 차면 큐를 비우고 종료 표시를 넣어 그 구독을 끊는다.
18. 시험·bench 용 읽기: `Kernel.instance_of(name)`, `ProcessPlugin.pid`, `ProcessPlugin.last_startup_ms`, `Clock.last_wait_timeout`, `Clock.pending()`, `Events.count()`.
19. bench: inproc 은 `handle` 직접 호출, process 시간 제한은 30초로 올려 1MB 왕복이 끊기지 않게 했다. 기동 시간은 process 5회 평균.
20. 화면: 이름은 sessionStorage(탭마다 다른 사용자). 남은 시간은 1초마다 글자만 다시 그린다(서버 조회 없음). dutch 현재가는 [새로 보기] 또는 이벤트 때 갱신한다.

## 8. 못 한 것·모르는 것

- 브라우저 조작 확인은 하지 않았다(지시대로 메인 에이전트·사용자 몫). `node --check ui/app.js` 구문 검사와 HTTP 시연만 했다.
- E7 의 hop 순서는 "adapter → kernel → registry → plugin" 이 연속이 아니라, 그 사이에 `kernel → internal:storage`(경매·입찰 읽기) hop 이 끼어 있다. 시험은 순서 부분열로 확인한다.
- bench 의 inproc 값은 코어(`kernel.call`) 경유 비용을 포함하지 않는다.
- remove 가드(진행 중 경매 확인)와 상태 변경 사이에 그 방식으로 경매가 새로 만들어지는 짧은 경합은 막지 않았다.
- Windows 11 + Python 3.14.2 에서만 돌려 봤다. 다른 OS 에서의 자식 프로세스 종료 동작은 확인하지 않았다.
