# 공통 구현 지시 (후보 A·B 공통) — 15판

교차 검토 1~7차, 과제 요구 대조(최종 검토), 단순화, 구현 검토 1차, 교차 검토 8~12차를 반영했다. 반영 내역: `교차검토-01-반영.md`.

## 목표

마이크로커널 아키텍처 스타일을 지키는 시스템을 만든다. 사용자가 브라우저에서 직접 조작해 쓸 수 있어야 한다. 테스트 통과만으로는 완료가 아니다.

## 고정 조건

- Python 3.14, 표준 라이브러리만 쓴다. 외부 패키지는 별도 프로세스 플러그인이 MANIFEST `requires` 에 적었을 때만 허용한다(후보 B 의 PDF 변환기 = PyMuPDF). 그 패키지가 없으면 그 플러그인만 `rejected` 가 된다.
- 외부 CDN·npm 을 쓰지 않는다. UI 는 정적 HTML/CSS/JS 다.
- 실행: `python app.py` → `http://127.0.0.1:<포트>`. 127.0.0.1 에만 bind 한다. 인자 `--port`, `--data <폴더>`, `--plugins <폴더>` 를 받는다(시험용).
- 한 파일에 몰지 않는다. 아래 폴더 구성을 따른다.
- 주석은 짧은 한국어로 쓴다. 코드는 단순하게 쓴다. 지시에 없는 추상화 계층을 만들지 않는다.

## 신뢰 범위

- 플러그인 작성자는 신뢰하는 로컬 개발자로 본다. 정적 검사와 `ctx` 는 구조 제약("코어를 통해서만")을 강제하는 장치다. 보안 샌드박스가 아니다.
- 프로세스 안 플러그인의 무한 루프·메모리 고갈은 막지 못한다. 별도 프로세스 플러그인만 시간 제한으로 끊는다. README 의 한계에 적는다.

## 구현 순서

시간이 모자라도 쓸 수 있는 상태가 남도록 이 순서로 만든다. 단계마다 시험을 같이 쓴다.

1. 계약·레지스트리·코어·내부 서버 1개·플러그인 1개·HTTP·도메인 화면 → 기본 흐름 하나가 브라우저에서 된다.
2. 설치·제거·다시 검색·다시 켜기와 플러그인 관리 화면.
3. 장애 격리, 별도 프로세스 어댑터.
4. 요청 경로 화면.
5. 나머지 플러그인, 시연용·예제 플러그인, bench, README.

## 폴더 구성

```text
<후보 폴더>/
  app.py                  시작점: 커널 생성(별도 프로세스 어댑터를 만드는 함수를 넘김) → 내부 서버 등록 → 플러그인 적재 → HTTP 서버 시작
  kernel/
    contract.py           계약: CONTRACT_VERSION, EXTENSION_POINTS, Plugin 추상 클래스, Rejected·Busy 예외
    registry.py           레지스트리: 이름 → 기록
    loader.py             plugins/ 검색, 정적 검사, MANIFEST 정적 읽기, 적재·해제
    constraints.py        정적 의존 검사 함수(적재·tools·시험이 같이 쓴다)
    kernel.py             코어 공통 장치: 대상 선택, 입출력 계약 검사, 내부 서버 호출 중계, 장애 격리, 추적
    flow.py               코어의 도메인 절차(A 경매 절차·잠금·마감, B 변환 절차). 플러그인·내부 서버 호출은 kernel.py 를 거친다
    context.py            플러그인에 주는 창구(ctx)
    plugin_host.py        별도 프로세스 쪽 실행기: 플러그인 적재 → JSON 한 줄 요청 처리
    trace.py              요청별 경로 기록(최근 200건, 메모리)
  internal/               내부 서버. 기본 동작에 포함, 클라이언트에 안 보임, 항상 적재
  plugins/                외부 서버. 파일 1개 = 플러그인 1개
  adapters/
    http_adapter.py       HTTP 요청 ↔ 코어 계약 변환(클라이언트 쪽 어댑터), SSE
    process_adapter.py    별도 프로세스 플러그인 ↔ 코어 계약 변환
  examples/               사용자가 plugins/ 에 복사해 넣어 보는 새 플러그인 예제 1개
  ui/                     index.html, app.js, style.css
  tools/
    check_constraints.py  kernel/constraints.py 를 plugins/ 전체에 돌리는 명령
    bench.py              인터랙션 비용 측정
  tests/                  unittest. fixtures/ 에 위반·장애 예제 플러그인
  data/                   실행 데이터와 plugins.json(.gitignore 대상)
  README.md               실행 방법, 구조, 플러그인 만드는 법(계약), 5분 시연 절차, 한계
```

- 계층 import: `kernel/` 은 `adapters/` 를 import 하지 않는다. 코어가 쓰는 예외는 `contract.py` 에 둔다. `app.py` 가 별도 프로세스 어댑터를 만드는 함수(`process_factory`)를 커널에 넘기고, loader 는 그 함수로 어댑터를 만든다. 시험도 같은 방법으로 커널을 만든다.

## 계약 (`kernel/contract.py`)

- `CONTRACT_VERSION = "1.0"`.
- 플러그인 파일은 최상위에 `MANIFEST = {...}`(리터럴 dict)와 `class Plugin(contract.Plugin)` 을 둔다.
  - 로더는 `MANIFEST` 를 `ast.literal_eval` 로 읽는다. 모듈을 실행하지 않고 이름·kind·runtime 을 안다.
  - 필수 키: `name`(파일 이름과 같음), `kind`(확장점 이름), `contract`, `version`, `description`.
  - 선택 키: `runtime`(`"inproc"` 기본 | `"process"`), `requires`(외부 패키지 import 이름 목록, process 일 때만), `timeout_sec`(process 일 때만), 후보별 키.
  - 타입: `name`·`kind`·`contract`·`version`·`description` 은 str 이고, `name` 은 `^[a-z0-9_]{1,40}$` 다. `runtime` 은 `"inproc"`·`"process"` 중 하나다. `requires` 는 str 목록이다. `timeout_sec` 는 0 초과 30 이하의 int 또는 float 다(bool 은 안 된다). 후보별 키의 타입은 후보 문서에 정한다.
  - `requires`·`timeout_sec` 는 process 일 때만 둔다. inproc 플러그인에 있으면 위반이다.
  - `requires` 에는 외부 패키지만 적는다. 이름의 최상위 부분이 표준 라이브러리(`sys.stdlib_module_names`)이거나 후보 폴더의 패키지·모듈(`kernel`, `internal`, `adapters`, `plugins`, `tools`, `tests`, `examples`, `app`)이면 위반이다.
  - 위반과 MANIFEST 읽기 실패(구문 오류, 리터럴 dict 가 아님)는 그 플러그인만 `rejected` 로 둔다. 시작 적재와 rescan 은 어떤 MANIFEST 에서도 예외로 멈추지 않는다.
- `Plugin.handle(self, op: str, payload: dict, ctx) -> dict` 하나만 구현한다.
- 오류는 두 종류다.
  - `contract.Rejected(reason)`: 입력·도메인 규칙 거부(예: 낮은 입찰가, 손상된 문서). 장애로 세지 않는다. HTTP 400(충돌은 409)과 사유를 돌려준다.
  - 그 밖의 예외: 플러그인 결함. 장애로 센다.
- `contract.Busy` 는 플러그인이 내지 않는다. 별도 프로세스 어댑터가 잠금 대기를 넘겼을 때 내고, 코어가 `busy` 로 바꾼다.
- `EXTENSION_POINTS = {kind: {op: {"in": {필드: 타입}, "out": {필드: 타입}}}}`. 후보 문서의 op 표가 이 값이다. 코어는 호출 전에 입력을, 호출 뒤에 출력을 이 표로 검사한다. 출력 위반은 장애로 센다. 검사는 필수 필드 존재와 `isinstance` 수준이면 된다.
- `ctx` 는 코어가 요청마다 만들어 주는 창구다. 플러그인이 코어 밖과 닿는 길은 이것뿐이다.
  - `ctx.log(msg)`: 코어 → 로그 내부 서버(후보 문서에 정함).
  - `ctx.internal(server, op, **args)`: 코어 → 내부 서버. 후보 문서의 허용 목록에 있는 (server, op) 만 받는다. 반환은 JSON 으로 바꿀 수 있는 값의 복사본이다.
  - DB 연결·레지스트리·커널·다른 플러그인 객체를 노출하지 않는다.
- 플러그인이 다른 플러그인을 부르는 창구는 두지 않는다. 여러 플러그인을 잇는 순서는 코어 절차가 정한다.

## 정적 의존 검사 (`kernel/constraints.py`)

`ast` 로 플러그인 파일을 검사한다. 적재(install·시작 적재) 때 모듈을 실행하기 전에 돌린다. `tools/check_constraints.py` 와 E5 시험도 같은 함수를 쓴다. 위반이면 `rejected` + 위반 줄 번호.

- 플러그인은 계산만 한다. 저장·파일·네트워크·프로세스는 코어와 내부 서버를 거친다. 그래서 import 는 허용 목록 방식이다.
- 허용 import: `kernel.contract`, 계산용 표준 모듈(`math`, `re`, `json`, `time`, `datetime`, `decimal`, `statistics`, `string`, `textwrap`, `unicodedata`, `html`, `html.parser`, `xml.etree.ElementTree`, `csv`, `io`, `base64`, `collections`, `itertools`, `functools`, `dataclasses`, `typing`, `enum`, `heapq`, `bisect`, `copy`), MANIFEST `requires` 에 적은 이름(runtime process 일 때만, 위 `requires` 규칙을 통과한 외부 패키지만). 목록은 `constraints.py` 의 상수 하나다. `from A import B` 는 `A` 또는 `A.B` 가 목록에 있으면 허용한다(예: `from xml.etree import ElementTree`).
- 위반: 그 밖의 import 전부(예: `os`, `sys`, `pathlib`, `shutil`, `sqlite3`, `socket`, `http`, `urllib`, `subprocess`, `threading`, `multiprocessing`, `ctypes`, `zipfile`, `pickle`, `importlib`, `plugins.*`, `internal.*`, `adapters.*`, `kernel.contract` 외 `kernel.*`), 상대 import, 이름 `open`·`__import__`·`exec`·`eval`·`compile` 사용.
- 한계: 허용 모듈 안에서의 우회(예: `__builtins__` 를 거친 접근)는 막지 못한다. 구조 제약 장치이고 샌드박스가 아니다(신뢰 범위). `kernel/plugin_host.py` 는 코어 코드라 이 검사 대상이 아니다.

## 코어가 하는 일 (`kernel/kernel.py`)

1. 확장점(kind) 목록과 계약 표를 가진다.
2. 대상 선택은 후보 문서의 규칙을 따른다. kind 만으로 고르지 않는다.
3. 호출 절차: 레지스트리 조회 → 상태 확인 → 입력 계약 검사 → 플러그인 호출 → 출력 계약 검사 → 결과 집계 → 응답.
4. 장애 판정:
   - 장애로 센다: `Rejected` 가 아닌 예외, 출력 계약 위반, 별도 프로세스의 시간 초과·비정상 종료·잘못된 응답.
   - 세지 않는다: `Rejected`.
   - 연속 3회 장애 → `disabled`. 성공하면 0으로 되돌린다.
   - `disabled` 는 사용자가 [다시 켜기]를 눌러야 `active` 가 된다. 자동 복구는 없다.
5. 선택 단계(후보 문서에 정함: A 알림, B 후처리)의 실패는 code 가 무엇이든(`rejected`·`fault`·`busy`·`unavailable`·`internal`) 핵심 결과를 깨지 않는다. 코어는 그 단계를 건너뛰고 결과에 경고(플러그인 이름, code, 사유)를 붙인다. 장애 집계는 4 의 규칙대로다(`fault` 만 센다).
6. 내부 서버 호출은 반드시 코어를 지난다.
7. 호출 결과: 성공이면 출력 dict 다. 실패면 `CallError(code, message)` 다. code 는 `rejected`(입력·도메인 거부, 장애 아님) / `fault`(장애로 셈) / `busy`(별도 프로세스 잠금 대기 초과, 장애 아님) / `unavailable`(`active` 가 아님, 또는 커널이 닫힘) / `internal`(내부 서버 실패, 예: 저장 오류. 플러그인 장애로 세지 않음)이다. HTTP 어댑터는 code 를 오류 응답의 `error.code` 로 쓴다. 상태 코드는 "HTTP API 공통" 의 표를 따른다.
8. 커널 종료(`shutdown`): 레지스트리 `Lock` 안에서 닫힘 표시를 먼저 세운다(생명주기 잠금은 기다리지 않는다). 그 뒤의 새 호출은 `unavailable` 이다. 진행 중 호출의 결과는 집계하지 않는다(종료 중의 실패가 `disabled` 로 저장되지 않게). 진행 중 호출이 실패로 끝나면 code 는 `unavailable` 이다. 그다음 생명주기 잠금을 얻어 모든 인스턴스를 정리한다(별도 프로세스는 자식 종료). 그때 진행 중이던 install 이 만든 인스턴스도 여기서 정리된다.

## 레지스트리와 생명주기

- 기록: name, manifest, state, generation(설치할 때마다 +1), failures, reason, loaded_at, inflight, contract(그 kind 의 입출력 계약 표), protocol(`inproc` = 함수 호출, `process` = 표준 입출력 JSON 한 줄). 레지스트리는 이름 → (입출력 계약, 접근 프로토콜, 상태)를 가진다.
- 상태: `available`(파일 있음, 미적재) / `active` / `disabled`(장애로 정지) / `rejected`(검사·계약 위반·적재 실패, 사유 기록).
- 생명주기 잠금: `install`·`remove`·`rescan`·`shutdown` 은 코어의 생명주기 잠금 하나로 한 번에 하나씩 진행한다. 후보 문서의 install 검사(예: B 의 형식 충돌)도 이 잠금 안에서 한다. 플러그인 호출은 이 잠금을 잡지 않는다.
  - install·remove·rescan 은 잠금을 얻은 뒤 커널이 닫혔는지 다시 본다. 닫혔으면 아무것도 바꾸지 않고 `unavailable`(503)로 거부한다.
- `install(name)`(= 다시 켜기): 정적 검사 → MANIFEST 검사(필수 키, 타입, `contract` major 일치, kind 가 확장점 목록에 있음) → 적재 → `active`, failures 0, generation +1.
  - 그 이름의 진행 중 호출이 남아 있으면 409("이전 호출이 끝나는 중")다. 옛 인스턴스가 있으면 먼저 정리한다(별도 프로세스는 자식 종료).
  - inproc: `importlib.util.spec_from_file_location("plugin_<name>_<generation>", 경로)` 로 실행한다. `sys.modules` 에 남기지 않는다. `Plugin` 이 없거나, `contract.Plugin` 의 하위 클래스가 아니거나, `handle` 이 추상이면 `rejected`.
  - process: 부모에서 import 하지 않는다. 자식을 띄우고 시간 제한 안에 `{"ready": true}` 를 받으면 `active`. 자식의 `plugin_host` 도 inproc 과 같은 클래스 검사를 하고, 어기거나 import 에 실패하면 `{"ready": false}` 를 보낸다. `{"ready": false}` 면(예: PyMuPDF 없음) 그 error 로 `rejected`.
  - 적재 중 구문 오류·예외는 그 플러그인만 `rejected` 로 두고 나머지 적재를 계속한다.
- `remove(name)`: 상태를 `available` 로 바꿔 새 호출을 막는다. 진행 중 호출은 이미 잡은 참조로 끝까지 처리한다. 진행 중 호출이 없으면 바로, 있으면 마지막 호출이 끝날 때 인스턴스를 정리한다(별도 프로세스는 자식 종료).
- 호출이 끝날 때의 inflight 감소와 인스턴스 정리는 호출을 시작할 때 잡은 기록에 한다. 이름으로 다시 찾지 않는다.
- `rescan()`: plugins/ 의 새 파일을 `available` 로 추가한다. 파일이 사라진 기록은 상태가 `available`·`rejected` 이고, 진행 중 호출이 0 이고, 정리할 인스턴스가 없을 때만 지운다. 아직 끝나지 않은 기록은 남긴다(그동안 같은 이름의 install 은 409). 재시작하지 않는다.
- 호출과 잠금: 레지스트리 `Lock` 안에서는 상태 확인·참조 확보·inflight 증감·집계(성공·실패 수, `disabled` 전환, 그에 따른 plugins.json 쓰기)만 한다. 플러그인 호출·자식 기동·모듈 적재는 이 잠금 밖에서 한다. 집계는 이 잠금 안에서 그 기록이 `active` 이고 커널이 닫히지 않았는지 확인하고 같은 잠금 안에서 반영한다. 닫힘 표시도 이 잠금 안에서 세우므로, 닫힘 뒤에 집계가 반영되는 일은 없다. 코어는 참조로 잡은 인스턴스 객체의 `handle` 을 부른다. 진행 중 호출이 남은 동안 install 이 409 이므로 옛 호출이 새 인스턴스에 섞이지 않는다.
- `<data>/plugins.json`: 플러그인 이름 → `{"state": "active" | "disabled", "reason"}`. install·remove·`disabled` 전환·다시 켜기 때 레지스트리 `Lock` 안에서 그때의 상태로 내용을 만들어 임시 파일에 쓰고 `os.replace` 로 바꾼다(쓰는 쪽이 모두 같은 잠금을 쓴다). 시작 때 `active` 만 적재한다. `disabled` 는 사유와 함께 그대로 두고 [다시 켜기]로만 복구한다.
- HTTP 서버는 `ThreadingHTTPServer`(`daemon_threads = True`) 다.
- 어댑터에는 업무 규칙을 두지 않는다. HTTP 어댑터는 요청을 코어 계약으로 바꿔 `flow.py` 에 넘기고, 결과를 응답으로 바꾸기만 한다.

## 별도 프로세스 플러그인 (`adapters/process_adapter.py`, `kernel/plugin_host.py`)

- 자식 실행: `sys.executable -m kernel.plugin_host <플러그인 파일>`, cwd = 후보 폴더, stderr 는 버린다(`DEVNULL`). plugin_host 는 `sys.stdout` 을 stderr 로 돌리고 원래 stdout 은 프로토콜에만 쓴다(플러그인의 `print` 가 프로토콜을 깨지 않게). 플러그인 import 에 성공하면 `{"ready": true}`, 실패하면 `{"ready": false, "error": "<예외 한 줄>"}` 을 한 줄 보낸다.
- 프로토콜(UTF-8 JSON 한 줄). 어댑터와 plugin_host 가 같은 인코딩 함수 한 쌍으로 payload·result 를 깊이와 상관없이 바꾸고 되돌린다. 코어 계약과 플러그인은 원래 값(`bytes`, 일반 dict)만 본다.
  - `bytes` → `{"$b64": "<base64>"}`.
  - 키가 하나뿐이고 그 키가 `"$b64"` 또는 `"$esc"` 인 일반 dict → `{"$esc": <그 dict 의 값들을 인코딩한 dict>}`.
  - 되돌릴 때: 키가 `"$b64"` 하나면 `bytes`, 키가 `"$esc"` 하나면 그 안의 dict 를 일반 dict 로(값만 되돌림). 그 밖의 dict 는 값만 되돌린다.
  - 값은 `dict`(키는 str)·`list`·`str`·`int`(-2**63 이상 2**63 미만)·`float`(유한값)·`bool`·`None`·`bytes` 만 쓴다. 이 검사는 `kernel/contract.py` 의 함수 하나(`check_values`)다. 코어의 출력 계약 검사는 runtime 과 상관없이 결과가 이 값들로만 되어 있는지 깊이 끝까지 본다(`tuple`, str 이 아닌 키, 범위 밖 int, NaN 등은 출력 위반 = 장애).
  - `plugin_host` 도 플러그인의 원래 결과를 직렬화하기 전에 같은 `check_values` 로 본다. 위반이면 결과 대신 `{"id","ok":false,"error":"출력 값 위반: ..."}` 를 보낸다(장애로 셈). JSON 직렬화가 위반을 지우지 못하게(tuple → list, 숫자 키 → 문자열) 하기 위해서다. 직렬화 자체가 실패해도 같은 오류 응답을 보낸다.
  - 시험: `meta` 에 `(1, 2)`, `{1: "x"}`, `2**63`, `float("nan")` 을 넣은 출력은 inproc·process 모두 출력 위반(장애 1회)이다. `2**63 - 1` 과 `-2**63` 은 두 runtime 에서 같게 왕복한다.
  - 그래서 inproc 과 process 에서 같은 출력이 같은 값으로 코어에 닿는다. 시험: `meta` 에 `{"$b64": "YQ=="}`·`{"$esc": 1}` 을 넣은 출력과 `bytes` 가 든 입력이 두 runtime 에서 같게 왕복한다.
- 메시지 모양:
  - 요청 `{"id","op","payload"}`
  - 응답 `{"id","ok":true,"result"}` / `{"id","ok":false,"rejected":true,"reason"}` / `{"id","ok":false,"error"}`
- 시간 제한: MANIFEST `timeout_sec`(기본 3초, 최대 30초).
- 호출 순서. 자식 하나에 `Lock` 하나를 두고 한 번에 한 요청만 보낸다.
  1. 잠금을 최대 시간 제한만큼 기다린다. 못 얻으면 `busy`(503, "플러그인이 바쁨, 다시 시도")다. 장애로 세지 않는다. 얻으면 어댑터가 닫혔는지 다시 본다. 닫혔으면 자식을 띄우지 않고 바로 오류를 낸다.
  2. 잠금을 얻은 뒤 시간 제한을 새로 잰다. 자식이 없으면 띄우고 준비 응답을 기다린다 → 요청 한 줄을 쓴다 → 응답 한 줄을 읽는다. 셋이 이 시간 제한을 나눠 쓴다.
  3. 시간 초과, 자식 종료, 잘못된 JSON, 응답 `id` 불일치, 재기동 실패: 그 자식을 정리한다(아래 "자식 참조"). 장애 1회로 센다. 다음 요청이 자식을 다시 띄운다.
- 자식 참조: 지금 자식의 `Popen`·읽기 큐와 닫힘 표시는 어댑터의 상태 잠금(자식 잠금과 별개, 짧게 잡음)으로 보호한다.
  - 자식을 띄우면 준비 응답을 기다리기 전에 상태 잠금 안에서 등록한다. 그때 닫혀 있으면 등록하지 않고 그 자식을 바로 정리한 뒤 오류를 낸다.
  - 정리 = 상태 잠금 안에서 참조를 떼어 낸 뒤, 잠금 밖에서 `kill()` → `wait(2)` → 파이프 닫기. 참조가 이미 떼어졌으면(다른 쪽이 정리함) 하지 않는다. 그래서 한 자식은 한 번만 정리된다.
- stdout 은 자식마다 새로 만든 읽기 스레드가 그 자식만의 큐에 줄을 넣는다. EOF·읽기 오류가 나면 끝 표시(`None`)를 넣고 끝난다. 요청 쪽은 `queue.get(timeout=남은 시간)` 으로 기다리고, 끝 표시를 받으면 "자식 종료"(3)로 처리한다. 그래서 자식이 죽으면 기다리던 요청이 바로 깨어난다. 쓰기는 요청 스레드에서 바로 한다(자식은 한 번에 한 요청만 받고 줄 전체를 읽은 뒤 처리하므로, 살아 있는 자식에 쓰기가 막히지 않는다).
- 호출자가 결과를 받기까지 최대 시간 = 잠금 대기(시간 제한) + 시간 제한 + 정리 2초(기본 8초). 앞 요청이 멈춰 있으면 뒤 요청은 기다리다 503 을 받거나, 앞 요청이 정리된 뒤 새 자식에서 처리된다. 어느 쪽도 뒤 요청의 장애가 아니다.
- `close()`: 자식 잠금을 기다리지 않는다. 상태 잠금 안에서 닫힘 표시를 세우고 자식 참조를 떼어 낸 뒤, 잠금 밖에서 그 자식을 정리한다. 진행 중이던 요청은 끝 표시를 받아 바로 오류로 끝난다. 기동 중이던 자식은 등록할 때 닫힘을 보고 스스로 정리된다. 닫힌 어댑터는 자식을 다시 띄우지 않고, 그 뒤의 `handle` 은 바로 오류를 낸다. remove·install 의 정리는 진행 중 호출이 없을 때만 일어나므로, 닫힌 어댑터에 호출이 닿는 경우는 커널 종료 중뿐이다(코어가 `unavailable` 로 바꾸고 집계하지 않는다).
- 별도 프로세스 플러그인은 `ctx` 를 쓰지 않는다. 필요한 데이터는 코어가 payload 에 넣는다. README 에 한계로 적는다.
- 코어 쪽에서 이 어댑터는 inproc 플러그인과 같은 `handle` 모양으로 보인다(어댑터 역할).

## 요청 경로 (`kernel/trace.py`)

- 요청마다 HTTP 어댑터가 trace_id(짧은 임의 문자열)를 만든다. 대상은 `/api/` 아래 모든 요청이다. GET 과, 403·404·411·413 처럼 코어에 닿기 전에 거부된 요청도 포함한다. 단 `/api/trace` 조회와 `/api/events`(A 의 SSE)는 기록하지 않는다. 정적 파일(`/`, `/ui/`)도 기록하지 않는다.
- trace_id 는 헤더 `X-Trace-Id` 에 넣고, JSON 응답이면(오류 응답 포함) 본문 `trace_id` 에도 넣는다. 코어에 닿기 전에 거부된 요청은 adapter hop 하나만 남는다.
- hop 기록: seq, parent(seq), from, to, op, ok, ms(`time.perf_counter` 기준). 실제로 지난 hop 만 남긴다. 플러그인이 내부 서버를 부르면 `plugin → kernel`, `kernel → internal` 두 hop 이다.
- 최근 200건만 메모리에 둔다.

## 저장 (내부 서버 공통)

- sqlite3 는 호출마다 새 연결(`timeout=5`)을 열고 닫는다. WAL 모드. 쓰기는 저장소 내부 `Lock` 으로 하나씩 한다. 연결 객체를 저장소 밖으로 주지 않는다.

## HTTP API 공통 (`adapters/http_adapter.py`)

- `GET /` → `ui/index.html`. `/ui/` 아래는 `index.html`·`app.js`·`style.css` 고정 목록만 준다.
- `GET /api/plugins` → 이름, kind, runtime, 상태, 버전, generation, 연속 실패 수, 사유, 확장점 계약.
- `POST /api/plugins/{name}/install`(다시 켜기 겸용), `POST /api/plugins/{name}/remove`, `POST /api/plugins/rescan`.
- `GET /api/trace?limit=50`, `GET /api/trace/{trace_id}`.
- 경로의 이름·ID 는 정규식(예: `^[a-z0-9_]{1,40}$`)으로 검사한다.
- 요청 본문은 `Content-Length` 만큼 읽는다. 없으면 411, 상한(기본 1MB, 후보 문서가 바꿈)을 넘으면 읽기 전에 413.
- 변경 요청(POST)은 `Host` 가 `127.0.0.1:<포트>` 또는 `localhost:<포트>` 이고, `Origin` 이 있으면 같은 출처일 때만 받는다(아니면 403).
- 오류 응답: `{"ok": false, "error": {"code", "message"}, "trace_id"}`. code 와 상태 코드:

  | code | 상태 |
  |---|---|
  | `rejected` | 400 |
  | `forbidden` | 403 |
  | `not_found` | 404 |
  | `conflict` | 409 |
  | `length_required` | 411 |
  | `too_large` | 413 |
  | `internal` | 500 |
  | `fault`·`busy`·`unavailable` | 503 |

- 처리 중 예상하지 못한 예외는 어댑터가 `internal`(500)로 바꾼다. 서버는 계속 동작한다.
- 짧은 주기 폴링을 쓰지 않는다. 실시간 갱신이 필요한 후보 A 만 SSE(`GET /api/events`)를 쓴다. 후보 B 는 자기 요청의 응답과 탭을 열 때의 조회로 화면을 갱신한다.
  - 구독자마다 크기 100 큐. 코어는 `put_nowait` 로 모든 구독자에 넣고 소켓 쓰기를 기다리지 않는다. 큐가 차면 그 구독을 끊는다.
  - 15초마다 주석 줄 heartbeat. 연결이 끊기면 구독을 해제한다.
  - 브라우저는 다시 연결되면 목록을 새로 조회한다.
  - 서버 종료 때 모든 구독 큐에 종료 표시를 넣어 깨우고, 소켓을 닫고, 등록을 해제한다(시험에서 서버가 멈추지 않고 내려가야 한다).

## UI 공통

- 탭 3개: [도메인 화면] · [플러그인 관리] · [요청 경로].
- 플러그인 관리: 목록 표, 설치·제거·다시 켜기 버튼, 다시 검색 버튼, 상태별 색, `rejected`·`disabled` 사유.
- 요청 경로: 최근 요청을 고르면 hop 목록(순서, 출발 → 도착, op, 성공 여부, ms)을 보여 준다. 도메인 화면의 결과마다 [경로 보기]로 그 trace 를 연다.
- 서버가 준 문자열(파일 이름, 사유, 설명)은 `textContent` 로만 넣는다.
- 오류는 화면에 문장으로 보인다. `alert()` 를 쓰지 않는다.

| E4 계약 위반 | `contract: "2.0"` → `rejected` + 사유. `handle` 미구현 → `rejected`. `contract.Plugin` 을 상속하지 않은 `Plugin` → inproc·process 모두 `rejected`. 적재 중 예외 → 그것만 `rejected`, 나머지 정상. 출력 계약 위반 → 장애로 집계. MANIFEST 타입 위반(예: `requires: None`, `timeout_sec: "3"`, 후보별 키의 타입 위반)이 든 파일이 plugins/ 에 있어도 앱이 시작되고 그 파일만 `rejected` |
| E5 의존 금지 | fixtures 위반 예제(다른 플러그인 import, `internal` import, 상대 import, `importlib`, `__import__`, `sqlite3` import, `os` import, `open` 사용, `requires` 에 없는 외부 패키지, `requires` 로 표준 모듈·후보 폴더 패키지를 연 파일(`["os"]`, `["internal"]`))를 모두 잡는다. 시험은 기대하는 fixture 이름 목록을 상수로 두고 그 파일이 모두 있는지 먼저 확인한다. 실제 plugins/ 는 0건. 위반 파일은 install 도 거부. 같은 `ast` 파싱으로 `kernel/` 의 파일이 `adapters` 를 import 하지 않는지 본다(kernel 에는 이 규칙 하나만 적용한다. 플러그인 import 허용 목록은 적용하지 않는다) |
| E6 보존 | 같은 data 폴더로 새 앱 인스턴스를 만들면 데이터·plugins.json(`disabled` 와 사유 포함)이 그대로다 |
| E7 HTTP·경로 | 실제 서버를 임시 포트(0)로 띄워 주요 API 왕복. 응답의 trace_id 로 `/api/trace/{id}` 를 읽어 hop 순서(adapter → kernel → registry → plugin …)를 확인. 출처가 다른 POST 는 403. GET 응답과 403·411·413 응답에도 `X-Trace-Id` 와 본문 `trace_id` 가 있고 `/api/trace/{id}` 로 읽힌다 |
| E8 동시성 | 멈추는 fixture 에 서로 다른 일반 입력으로 동시 요청 10개 → 모두 성공하고 각 응답이 자기 입력에 맞는다. hang 요청 1개를 보내고 어댑터의 `busy` 가 참이 되기를 기다린다(2초 안에 못 보면 시험 실패) → 일반 요청 2개를 보낸다 → hang 요청은 6초 안에 `fault`, 일반 요청은 각각 성공 또는 `busy` 이고 9초 안에 돌아온다(`fault` 는 hang 1건뿐) → 상태 `active` → 다음 일반 요청 성공, 연속 실패 수 0 |

- 멈추는 fixture(E2·E3·E8): `tests/fixtures/` 의 시험용 플러그인이다. 표준 라이브러리만 쓰고 `runtime: "process"` 다. 그 후보의 별도 프로세스 확장점 계약을 그대로 따른다(A: `notifier` 의 `on_outbid`, B: `converter` 의 `convert`). 입력 필드 하나(A: `item`, B: `filename`)가 `"hang"` 이면 응답하지 않고, `"slow"` 면 1초 뒤에, 그 밖에는 바로 계약에 맞는 출력을 돌려준다. MANIFEST `timeout_sec` 는 3 이다. 붙잡는 fixture(E3 shutdown (가))는 같은 코드에 이름과 `timeout_sec: 10` 만 다른 사본이다. 시간 제한이 shutdown 보다 먼저 오지 않게 한다. 출력에는 입력 필드 값을 넣는다(E8 에서 응답이 자기 입력에 맞는지 본다). 시험은 HTTP 대신 코어의 이름 지정 호출 함수 `kernel.call(plugin_name, op, payload)` 로 부른다. 이 함수는 "코어가 하는 일" 3 의 호출 절차(상태 확인 → 입력 계약 검사 → 호출 → 출력 계약 검사 → 집계) 그대로이고, 대상 선택만 건너뛴다.
- 시험 쪽 장벽(E2·E3 (나)): 시험이 그 기록의 인스턴스 객체의 `handle` 속성을, `threading.Event` 가 설정될 때까지 기다린 뒤 원래 `handle` 을 부르는 함수로 바꾼다. 10초 안에 설정되지 않으면 원래 `handle` 을 부르지 않고 시험을 실패로 끝낸다(감싼 함수가 실패를 기록하고, 시험이 그 기록을 단언한다). 코어 코드는 바꾸지 않는다. 시험은 `finally` 에서 Event 를 설정한다. 호출 시간이 시험의 실행 속도에 기대지 않는다.
- 어댑터는 시험용으로 다음을 읽기 전용으로 내보인다. `busy`(자식 잠금이 잡혀 있음, `Lock.locked()`), `waiting`(요청 한 줄을 다 쓴 뒤 응답 큐를 기다리는 동안만 참), `pid`(지금 등록된 자식의 pid, 없으면 `None`).
- 시험은 임시 폴더(`--data`, `--plugins`)를 쓴다. 저장소의 `data/`·`plugins/` 를 바꾸지 않는다.
- 사용 확인: 구현자는 서버를 띄워 README 의 5분 시연 절차를 HTTP 로 따라가 본다. 브라우저 조작 확인은 메인 에이전트와 사용자가 한다.
- `tools/bench.py`: 같은 fixture 플러그인 파일 하나를 inproc 과 process 로 각각 적재해 같은 op 를 200회 호출한다. 표: 자식 기동 시간(준비 응답까지), 호출당 평균·p95 ms(payload 1KB·100KB·1MB).

## 금지

- 한 파일에 몰기, `requires` 밖 외부 패키지, CDN.
- 시험에서 고정 포트 사용, 저장소 `data/`·`plugins/` 수정.
- 프로세스 종료는 자기가 띄운 자식의 `Popen` 핸들로만 한다. 이름으로 종료(`taskkill /IM`, `Stop-Process -Name`, `pkill`) 금지.
- 후보 폴더 밖 쓰기 금지. git commit·push 금지.
- 코드·문서에 개인 정보·절대 경로 금지.
